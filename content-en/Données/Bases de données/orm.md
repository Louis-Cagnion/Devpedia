# The ORM: mapping objects onto relational tables

An object-oriented program manipulates classes and instances; a relational database stores tables and rows. The two models don't overlap naturally (a relationship between two objects isn't a foreign key, class inheritance has no direct [SQL](/?c=langages&s=domain-specific-languages-dsl&p=sql) equivalent): an **ORM** (*Object-Relational Mapping*) automates the translation between the two, so code is written against objects rather than manual SQL queries.

## What an ORM automates

An ORM maps a class to a table, an instance to a row, an attribute to a column, then generates the matching SQL itself:

```text
Object model:                     Relational model:

class User {                 <->  TABLE users (
  id                                id INTEGER PRIMARY KEY,
  email                             email TEXT,
  orders: Order[]                   ...
}                                  )
                                   TABLE orders (
                                     user_id INTEGER REFERENCES users(id),
                                     ...
                                   )
```

```javascript
// With an ORM (Prisma example): an object, not a hand-written SQL query
const user = await prisma.user.create({
  data: { email: "alice@example.com" }
});

// The SQL generated by the ORM, never written directly:
// INSERT INTO users (email) VALUES ('alice@example.com');
```

Basic [CRUD](/?c=ia&s=production-et-gouvernance&p=gouvernance-des-donnees) (create, read, update, delete) is generated automatically for every declared table, without writing a single query yourself for these simple cases.

## Migrations: versioning the schema like code

A database schema evolves with the application (a new column, a new table, a modified constraint). A **migration** is a script that describes this change incrementally and reversibly, tracked by [Git](/?c=git&p=git) the same way as application code:

```text
migrations/
  20260101_create_users.sql
  20260115_add_email_verified_column.sql
  20260201_create_orders_table.sql
```

Each migration applies in order, once, on every environment (development machine, staging, production): the database schema becomes reproducible from the migration history, instead of depending on a chain of manual changes that were never tracked.

> **Pitfall:** modifying the schema directly in production (an `ALTER TABLE` run by hand), without a matching versioned migration. The real schema then silently drifts from what the code describes, until a deployment on another environment fails or reproduces a different state.
>
> **Best practice:** route every schema change through a versioned migration, including a seemingly minor tweak, exactly like a code change goes through a commit.

## Type safety: catching an error before execution

An ORM like Prisma generates types from the database schema: a typo in a column name or a wrong value type is caught at compile time, before the program even runs, rather than when the invalid SQL query fails in production:

```javascript
prisma.user.create({ data: { emial: "alice@example.com" } });
// Immediate compile error: "emial" does not exist on this model
```

A hand-written SQL query in a string offers none of these guarantees: the same typo would only be caught at runtime, if at all.

## The classic pitfall: the N+1 problem

Accessing a relation (a user's orders, for example) inside a loop often triggers a separate query on **every iteration**, instead of a single query fetching everything at once:

```javascript
const users = await prisma.user.findMany(); // 1 query

for (const u of users) {
  const orders = await prisma.order.findMany({ where: { userId: u.id } });
  // 1 extra query PER user: N users -> N+1 queries total
}
```

> **Pitfall:** loading a relation inside a loop without noticing, because the ORM makes that call as syntactically simple as accessing a plain attribute. With 1000 users, this code triggers 1001 separate queries where a single one, with a join, would suffice.
>
> **Best practice:** preload the needed relations in a single query (`include`/`with`/eager loading, depending on the ORM), before the loop, instead of letting the ORM trigger a new one on every iteration.

```javascript
// 1 single query, with a join, instead of N+1
const users = await prisma.user.findMany({ include: { orders: true } });
```

## When an ORM isn't the right answer

An ORM excels at simple [CRUD](/?c=ia&s=production-et-gouvernance&p=gouvernance-des-donnees), but sometimes forces a complex analytical query (multiple aggregations, windowing, many joins; see [Data warehouse vs data lake](/?c=bases-de-donnees&p=entrepot-vs-data-lake) for this kind of OLAP need) into a syntax designed to manipulate objects, not to express an analytical query. Raw SQL, or a *query builder* closer to SQL than a full ORM, often stays clearer and more performant for this kind of case.

## 📋 Summary

| | |
|---|---|
| **To remember** | An ORM automatically translates between the code's object model and the database's relational model (class/table, instance/row). Migrations version the schema like code. Type generation catches a schema error at compile time rather than at runtime. |
| **Usable tools** | An ORM (Prisma and equivalents) for everyday CRUD; versioned migrations for every schema change; relation preloading (`include`/`with`) to avoid one query per iteration. |
| **Pitfalls to avoid** | Modifying the schema in production without a versioned migration. Loading a relation inside a loop (N+1 problem). |
| **Best practices** | Route every schema change through a versioned migration. Preload the needed relations in a single query, before the loop that uses them. Reserve raw SQL for complex analytical queries that the ORM's abstraction would make less clear. |
