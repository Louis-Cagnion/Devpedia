# Agents: Tool/Reflection Loop and Orchestration

An LLM on its own simply generates text from text (see [LLM in Production](/?c=ia&s=nlp-llm&p=llm-en-production)): it cannot query an up-to-date database, perform a reliable calculation, or send an email. An **agent** is the way to overcome this limitation: we provide the model with **tools** it can choose to call upon, and a loop that repeats the operation until it has enough information to respond.

## Providing a tool for a model: function calling

The basic mechanism is called *function calling* (or *tool use*): in addition to the prompt, the model receives a structured description of one or more available functions (their names, what they do, and the parameters they expect), a simple [JSON](/?c=infrastructure&p=json) document:

```json
{
  "name": "get_weather",
  "description": "Returns the current weather for a given city",
  "parameters": {
    "city": { "type": "string", "description": "City name" }
  }
}
```

The model cannot execute this function on its own: it merely **determines** that it would be useful here and generates the arguments to be passed to it, also in JSON:

```json
{ "call": "get_weather", "arguments": { "city": "Montpellier" } }
```

It is the code surrounding the model that receives this decision, actually executes the corresponding function (Python, the [HTTP](/?c=infrastructure&p=api-et-http) call, the SQL query...), and returns its result to the model so that it can continue.

> **Pitfall:** blindly trusting the arguments produced by the model before passing them to the actual function: the model never truly “knows” what a function does beyond its textual description; an imprecise or ambiguous description results in calls with the wrong arguments just as surely as a poorly documented function misleads a human developer who reads only its signature.
>
> **Best practice:** Validate the received arguments (types, expected values) before executing the actual function, just as you would validate input from any untrusted source.

## A free-form parameter rather than a fixed value: where does the variation come from?

The `city` parameter in the previous example takes values only from a limited and predictable set (city names). There is no requirement for a parameter to be so restricted: it can just as easily be **free-form text written by the model itself**, such as a shell command, an SQL query, or a code snippet:

```json
{
  "name": "execute_bash",
  "description": "Executes a shell command and returns its standard output",
  "parameters": {
    "command": { "type": "string", "description": "The command to execute" }
  }
}
```

The function that actually executes this tool (on the code side, not the model side) is as basic as it sounds: most often a simple `subprocess.run(command)` that runs the received string without understanding any of it. It never changes between calls. What varies is the **content of `command`**, recomposed by the model with each call based on what it has just learned:

```text
Turn 1 -> the model generates: { "command": "ls -la /var/log" }
       -> result: the list of log files
Turn 2 -> the model generates: { "command": "grep ERROR /var/log/app.log | tail -20" }
       -> same tool, same Python function behind it, completely different command
```

This is exactly what allows an agent to generate different Bash commands each time for the same tool: the function being executed doesn’t change (it simply carries out the command), but the text it receives is generated on the fly by the model, much like a human who would type a different command based on what they just saw displayed in their terminal.

> **Pitfall:** a free-form parameter carries a much higher risk than a restricted one: there is no guarantee that the text generated by the model is correct, or even harmless. A shell command generated by the model may contain, either accidentally or through manipulation (see [prompt injection](/?c=ia&s=nlp-llm&p=prompt-injection)), the same special characters that make [command injection](/?c=shells&s=bash&p=variables) possible.
>
> **Best practice:** Treat any free-form parameter generated by a model with the same caution as unvalidated user input: never blindly interpolate it into a command or query without taking the same precautions as you would elsewhere.

## The Reflection/Action Loop (ReAct)

Simply having the tools available (as described in the previous section) is not enough, in and of itself, to create an agent: a program that calls a fixed list of functions in an order predefined by a developer remains a traditional script, even if it consults an LLM at one stage. What defines an agent is that **the model decides for itself, at each step, what to do next** (which tool to call, with which arguments, or whether it’s finished), based on the results of the previous steps, without any human having written this sequence in advance. An agent is therefore this sequence repeated until the model determines it has enough information to respond, rather than a simple question-and-answer exchange or a fixed-sequence script:

```text
1. The model receives the question and the history
2. It decides: answer directly, OR call a tool
3. If a tool is called: the code executes it, the result is added to the history
4. Back to step 1, with this new piece of context
```

This pattern, often called *ReAct* (*Reasoning + Acting*), enables multi-step sequences: searching for information, using it to refine a second search, calculating an intermediate result, and then constructing the final response, with each step relying on the actual result of the previous one rather than on an assumption made by the model.

## Risks specific to a loop controlled by a non-deterministic model

A classic loop terminates based on a condition known in advance. An agent loop stops when the model **decides** to stop, a decision that is not guaranteed, made by a system that can make mistakes (see the limitations in the chapter [LLM in Production](/?c=ia&s=nlp-llm&p=llm-en-production)).

> **Pitfall:** an unbounded loop. Without an explicit upper limit on the number of iterations, a model that fails to terminate may repeat calls indefinitely.
>
> **Best practice:** Enforce a hard limit (number of iterations, token budget), just as you would a timeout on any network call.

> **Pitfall:** a cost that quietly adds up. Each iteration of the loop is a separate LLM call, billed independently (see [production costs](/?c=ia&s=nlp-llm&p=llm-en-production)): responding in a single iteration costs the price of one call; an agent that needed 20 iterations to arrive at its answer incurs 20 charges, even if the user asked only one question. In practice, the multiplier is worse than a simple x20: at each turn, the entire history of previous turns (initial question, tool calls, results obtained) is fed back into the model as input so that it retains context, so the prompt for round 20 is much larger than that for round 1, meaning that the total cost grows faster than the number of rounds itself.
>
> **Best practice:** Monitor the cumulative cost of an agent loop in production (see [cost monitoring](/?c=ia&s=production-et-gouvernance&p=gestion-dun-llm)), not just the average cost per question: the benefit of an agent is not always proportional to this additional cost.

> **Pitfall:** irreversible actions decided by a fallible system. An agent who can send an email or modify a database may also do so in error, based on flawed reasoning.
>
> **Best practice:** require human confirmation before any action with real-world consequences (financial, destructive, publicly visible); for a system classified as high-risk, this is an explicit legal requirement under [European AI regulations](/?c=ia&s=production-et-gouvernance&p=reglementation-europeenne-ia), not just a best practice.

## One agent, or several who share the work?

Two architectures compete for complex tasks:

| | A general-purpose agent | Several specialized agents |
|---|---|---|
| Principle | A single model, many tools available | Each agent has a specific role (research, writing, verification) and passes the results on to the next agent |
| Advantage | Easier to build and maintain | Each agent remains focused on a task it handles best, making it easier to evaluate individually |
| Disadvantage | A system prompt that grows with each added tool, to the point of diluting the model’s focus | Coordination must be explicitly designed (who speaks to whom, in what order, what to do if an agent fails) |

The choice follows the same logic as elsewhere in software architecture: a single general-purpose agent is sufficient as long as the task remains limited; specialization is warranted when complexity (number of tools, length of reasoning) begins to compromise the reliability of a single agent.

## Coordinating Multiple Agents: Common Patterns

"Explicitly designed coordination" encompasses, in practice, a few recurring patterns that are not mutually exclusive:

| Pattern | Principle | When to use |
|---|---|---|
| **Sequential processing** (*pipeline*) | The output of Agent A becomes the input for Agent B, in a fixed order (e.g., a "research" agent followed by a "writing" agent) | The steps are known in advance and always execute in the same order |
| **Orchestrator / Workers** | An “orchestrator” agent breaks down the task, decides which specialized agent to call and in what order, and then combines their results | The order of the steps depends on the task itself and cannot be fixed in advance |
| **Shared state** (*blackboard*) | Agents do not communicate directly with one another: they read from and write to a shared space (a database, a shared document), with each agent reacting to what others have posted there | Multiple agents must collaborate without a strict order of dependency, with each contributing when it has something to contribute |
| **Evaluator / Optimizer** | An agent generates an initial version; a second agent (the same model or a different one) evaluates it based on explicit criteria; then a new version incorporates this feedback, repeated until a termination criterion is met (see details in [The Agent-Based AI Assistant in the Terminal](/?c=ia&s=applications-llm&p=assistant-agentique-terminal)) | Output quality matters more than latency, and an explicit evaluation criterion exists (checklist, tests, expected format) |

> **Pitfall:** particularly with a shared state, there is nothing to prevent two agents from acting based on information that has become inconsistent with each other (one read the state before the other modified it): the same class of problem as concurrent access to a shared resource in traditional programming.
>
> **Best practice:** explicitly specify, for each of these three patterns, what to do if an agent fails or produces an unusable result (an interposed "verifier" agent, a format check at the end of each step), and who has the final say in the event of concurrent writes: the same safeguards as for traditional concurrent access (locking, only one agent allowed to write at a time).

## Key Takeaways

| | |
|---|---|
| **Key Takeaway** | An agent provides tools to an LLM (function calling) and lets it decide for itself, at each step, which tool to call and when to stop (ReAct loop), as opposed to a pre-written script with a fixed sequence. |
| **Available Tools** | A JSON description of each available tool (name, parameters, description); a limit on the number of iterations or budget to cap the loop. |
| **Pitfalls to Avoid** | Blindly trusting arguments generated by the model. An unescaped parameter (command, query) processed without the same precautions as an untrusted input. An unbounded loop. A cost that accumulates silently. An irreversible action decided without human confirmation. |
| **Best Practices** | Validate received arguments before executing a tool. Treat any free parameter generated by the model as an untrusted input. Enforce a hard limit on the number of iterations. Monitor the cumulative cost of a loop. Require human confirmation before any action with real-world consequences. |
