# Reading System State

Administering a server means being able to answer simple questions at any time: how much memory is still free? Is the disk approaching saturation? Who's connected right now? This chapter covers where to find this information; broadcasting it automatically (for example, a message sent every 10 minutes) is the job of [cron automation](/?c=shells&s=bash&p=automatisation-cron), already covered separately.

## `/proc`: the filesystem that isn't really one

On Linux, `/proc` is a **virtual filesystem**: its files don't exist on any disk, the kernel generates them on the fly at every read to expose its internal state (processes, memory, detected hardware). Reading it works exactly like reading a regular file (`cat`, `grep`, redirections), but its content reflects the state of the system **at the exact moment** it's read, never a cached value.

```bash
cat /proc/loadavg
# 0.15 0.10 0.05 1/523 12345
```

## Where to find each piece of information

| Information | Dedicated command | Equivalent `/proc` file |
|---|---|---|
| Architecture and kernel | `uname -a` | `/proc/version` |
| Number of physical CPUs | `lscpu` | `/proc/cpuinfo` (count distinct `physical id`) |
| Number of virtual CPUs (vCPU) | `nproc` | `/proc/cpuinfo` (count `processor` entries) |
| Memory used (%) | `free -m` | `/proc/meminfo` (`MemTotal` / `MemAvailable`) |
| Disk space used (%) | `df -h` | - (managed by the mounted filesystem itself, not `/proc`) |
| CPU load | `uptime` | `/proc/loadavg` |
| Last reboot date | `who -b` or `uptime -s` | `/proc/uptime` (seconds elapsed since boot) |
| LVM state | `lvs` / `vgs` / `pvs` (see [Partitioning and LVM](/?c=administration-systeme&p=partitionnement-et-lvm)) | - |
| Active connections | `ss -t` | `/proc/net/tcp` |
| Logged-in users | `who` or `w` | - |
| IPv4 and MAC address | `ip addr` | `/proc/net/dev` (lists interfaces, without their addresses) |

> **Note:** there are two ways to get the same information: a dedicated command (`free`, `df`, `uptime`...), designed to be readable directly, or the corresponding `/proc` file, to parse yourself. A dedicated command is preferable whenever one exists; `/proc` is mainly useful when no suitable command is available, or for a script that needs a precise raw value rather than already-formatted text.

## Example: extracting a precise metric

```bash
# percentage of memory used, computed from /proc/meminfo
total=$(awk '/MemTotal/ {print $2}' /proc/meminfo)
available=$(awk '/MemAvailable/ {print $2}' /proc/meminfo)
echo "$(( (total - available) * 100 / total ))% memory used"
```

This kind of extraction (via `awk`, see [Text Processing](/?c=shells&s=bash&p=traitement-de-texte)) is the basis of a system monitoring script: each metric from the table above is read, formatted, then assembled into a single message, which [`cron`](/?c=shells&s=bash&p=automatisation-cron) can then broadcast periodically (for example via `wall`, which displays a message to all logged-in users).

> **Pitfall:** parsing a `/proc` file's format directly (number of columns, field order) without checking that it stays stable: this format isn't guaranteed to be identical across all kernel versions. A script that works on one machine can fail silently on another.
>
> **Best practice:** prefer a dedicated command when one exists (it encapsulates format variations itself), and only read `/proc` directly as a last resort, testing the script on the actually targeted distribution.

## 📋 Summary

| | |
|---|---|
| **Key takeaways** | `/proc` is a virtual filesystem generated by the kernel, which reflects the system's state in real time; every common system metric (CPU, memory, network, users) is accessible either through a dedicated command or through a corresponding `/proc` file. |
| **Tools you can use** | `uname`, `lscpu`, `nproc`, `free`, `df`, `uptime`, `who`/`w`, `ss`, `ip addr`, `lvs`/`vgs`/`pvs`. |
| **Pitfalls to avoid** | Parsing a `/proc` file without checking the stability of its format across distributions/kernel versions. |
| **Best practices** | Prefer a dedicated command over `/proc` when one exists; test any monitoring script on the actually targeted distribution. |
