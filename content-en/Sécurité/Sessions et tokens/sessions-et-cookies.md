# Sessions and Cookies

The chapter on [APIs and HTTP](/?c=infrastructure&p=api-et-http) covers how a client sends a request and gets a response. What it doesn't say yet: HTTP is a **stateless** protocol, each request is handled independently of the ones before it, as if the server had total amnesia between two requests. Without an extra mechanism, a site would have to ask for the username and password again on every single page.

```text
Request 1 : POST /login (email + password)   -> server checks, responds "login successful"
Request 2 : GET /profile                      -> server knows NOTHING about request 1:
                                                   as far as it's concerned, this is an anonymous visitor
```

## The Solution: An Identifier the Client Sends Back on Every Request

After a successful login, the server creates a **session**: a storage space kept on its own side, tied to that specific visitor (their user ID, their permissions...). In return, it hands the client a **session identifier**, a unique value the client will then send back on every request, so the server knows which session to look up:

```text
Client                                     Server
------                                     ------
POST /login (email + password)       ->    checks, creates a session,
                                            responds with the identifier
                                      <-    Set-Cookie: session_id=a8f3d9...

GET /profile
Cookie: session_id=a8f3d9...         ->    looks up session a8f3d9...,
                                            knows it's this user
                                      <-    responds with their profile
```

## The Cookie: What Carries the Identifier

A **cookie** is a small piece of data the server asks the browser to keep, and which the browser sends back automatically on every request to the same site: it's the most common vehicle for carrying the session identifier from one request to the next, without the developer having to handle it manually on every call.

This chapter stays deliberately independent of the language used: see [Manage Connections](/?c=langages-de-programmation&s=php&p=connexions) for the concrete [PHP](/?c=langages-de-programmation&s=php&p=php) implementation (`setcookie()`, `$_SESSION`, the automatically generated `PHPSESSID` identifier).

## Why the Session Identifier Must Be Unpredictable

If an attacker could guess a valid session identifier (for example a simple counter: `1`, `2`, `3`...), they'd gain access to the corresponding account without knowing either the victim's email or password. The session identifier is a use case cited directly in the chapter on [randomness and generators](/?c=representation-des-donnees&p=aleatoire-et-generateurs): it must be generated by a **cryptographic** random generator, never a simple counter or a classic generator.

## Session Theft: The Real Everyday Risk

Even with a perfectly unpredictable identifier, an attacker who manages to **steal** the cookie of an already logged-in user (unencrypted network, an [XSS flaw](/?c=langages-de-programmation&s=php&p=securite#htmlspecialchars-protecting-against-xss-flaws) reading `document.cookie`, a poorly secured shared device) gets complete, immediate access to the account, without ever needing the password: this is **session hijacking**.

| Risk | What it lets an attacker do |
|---|---|
| Predictable session identifier | Guess a valid identifier without stealing anything |
| Stolen session cookie | Reuse an already-valid identifier, without guessing it or knowing the password |

> **Pitfall:** assuming an unpredictable session identifier is enough to secure a session. An unpredictable identifier stops it from being *guessed*, but doesn't protect against it being *stolen* once it exists.
>
> **Best practice:** only transmit the session cookie over HTTPS, block access to it from [JavaScript](/?c=langages-de-programmation&s=javascript&p=javascript), and restrict it to requests genuinely coming from the site (see the `secure`/`httponly`/`samesite` options detailed in [Manage Connections](/?c=langages-de-programmation&s=php&p=connexions)).

## 📋 Summary

| | |
|---|---|
| **Key takeaways** | HTTP is stateless: without an extra mechanism, the server remembers nothing between two requests. A session (server-side) tied to an identifier carried by a cookie solves this problem: the client sends the identifier back on every request, the server looks up the matching session. |
| **Tools you can use** | A cryptographic random generator for the session identifier; the `secure`/`httponly`/`samesite` cookie options to limit the risk of theft. |
| **Pitfalls to avoid** | A predictable session identifier (a counter, a guessable value). Believing an unpredictable identifier is enough, without also protecting against the cookie itself being stolen. |
| **Best practices** | Generate the session identifier with a CSPRNG. Secure the session cookie (HTTPS only, inaccessible to JavaScript, limited to requests from the site). |
