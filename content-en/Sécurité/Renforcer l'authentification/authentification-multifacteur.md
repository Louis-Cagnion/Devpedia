# Multi-Factor Authentication

The chapter [Authentication vs Authorization](/?c=authentification&s=fondamentaux&p=authentification-vs-autorisation) distinguishes three families of proof of identity: something you know, something you have, or something you are. Most accounts rely on only one (the password): a single secret, enough to compromise everything if it leaks. **Multi-factor authentication** (MFA) requires at least two proofs **from different families** before granting access.

> **Pitfall:** confusing "two checks" with "two factors." A password followed by a secret question ("what's your first pet's name?") is still a single factor (something you know) repeated twice: both proofs belong to the same family, and an attacker who can guess or find one has a good chance of finding the other by the same means (a social media search, for instance).
>
> **Best practice:** combine two factors from genuinely different families (a password + a code generated by an app, for example), never two variants of the same type of proof.

## Why Combining Two Factors Drastically Reduces the Risk

Password leaks are massive and frequent: entire databases of stolen passwords circulate, and a password reused across multiple sites can be tested automatically everywhere it was used. Without a second factor, a compromised password is enough to open the account. With a second factor from another family, the attacker must also physically possess the object (phone, security key) or the victim's biological trait: a significantly harder obstacle to clear remotely.

## Common Second-Factor Methods

| Method | Principle | Main weakness |
|---|---|---|
| SMS code | A code sent by text message to the user's phone | Vulnerable to [*SIM swapping*](https://en.wikipedia.org/wiki/SIM_swap_scam) (transferring the phone number to a SIM card controlled by the attacker) |
| Authenticator app ([TOTP](https://en.wikipedia.org/wiki/Time-based_one-time_password)) | A locally generated code, changing every 30 seconds | Still usable if the user enters it on a fake site ([phishing](https://en.wikipedia.org/wiki/Phishing)) |
| Physical security key ([FIDO2](https://en.wikipedia.org/wiki/FIDO2_Project)/[WebAuthn](https://en.wikipedia.org/wiki/WebAuthn)) | A physical object that cryptographically responds to a request from the site | Cost of the object, must be physically present |

## TOTP: Generating a Code Without a Network Connection

A **TOTP** (*Time-based One-Time Password*) code works without the app and the server communicating at generation time: both share a secret, established once (typically via a QR code scanned during activation), then each independently computes a code from that secret and the current time, rounded to a 30-second window:

```text
Shared secret (established once, at activation)
        |
        +-- App    : computes a code from the secret + the current time
        +-- Server : computes the same code, independently, with the
                      same secret + the same time

Both codes match without any message having passed between the two
```

This is what lets an authenticator app work even without an internet connection: it only needs a roughly synchronized clock, not a network exchange.

## The Physical Security Key: The Most Robust Protection Against Phishing

A TOTP code remains vulnerable if the user enters it themselves on a fake site that mimics the real one (a [phishing](https://en.wikipedia.org/wiki/Phishing) attack): nothing technically prevents typing the right code into the wrong place. A physical security key (FIDO2/WebAuthn) eliminates this risk differently: it cryptographically verifies the exact address of the site requesting it, and refuses to respond if the address doesn't match the one registered originally, even if the fake site looks visually identical to the real one.

> **Pitfall:** setting up robust multi-factor authentication, but leaving an account recovery method that's too permissive ("lost your second factor? answer these security questions"). An attacker then targets that weaker recovery path instead of attacking the second factor itself, which cancels out the entire benefit of MFA.
>
> **Best practice:** apply the same level of rigor to the second-factor recovery process as to authentication itself, rather than treating it as a mere secondary safety net.

## 📋 Summary

| | |
|---|---|
| **Key takeaways** | Multi-factor authentication requires at least two proofs of identity from different families (know/have/are), not two variants of the same type. A compromised password is no longer enough on its own: the attacker must also possess the second factor. |
| **Tools you can use** | A TOTP app (locally generated code, no network needed); a FIDO2/WebAuthn physical security key for the most robust protection against phishing. |
| **Pitfalls to avoid** | Confusing two checks of the same factor with a true second factor. Leaving an account recovery path that's too permissive, bypassing MFA. |
| **Best practices** | Combine two factors from genuinely different families. Apply the same level of rigor to the recovery process as to authentication itself. |
