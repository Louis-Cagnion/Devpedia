## Bug de rendu : séparateur `---` affiché en texte littéral (2026-08-20)

Repéré en relisant le rendu de `entiers-et-debordements.md` après l'ajout de la section arithmétique en précision arbitraire : le `---` qui sépare le `## Résumé` intermédiaire du `## 📋 Récapitulatif` final (convention déjà utilisée par 226 fichiers en FR, autant sinon plus par langue traduite) s'affichait comme le texte littéral "---" plutôt qu'une ligne horizontale. `parseAppendText` (`js/parser.js`) ne traitait aucun cas "ligne réduite à `---`" : elle tombait dans la branche générique `<p>`. Corrigé en ajoutant un cas dédié avant la détection de tableau (une ligne `---` seule n'a jamais de `|`, aucun risque de collision) qui génère un `<hr>`, plus une règle CSS minimale (`border-top`, pas de style avant). Vérifié par grep sur les 4 langues : chaque occurrence d'une ligne `---` isolée dans tout `content(-<lang>)/` est bien suivie d'un titre `##`, aucun usage décoratif détourné qui aurait pu être cassé par ce changement.

## Revue de la table de prononciation TTS (2026-08-15)

Écart repéré en revoyant `CONTEXT_OPERATOR_SPEECH`/`GLOBAL_OPERATOR_SPEECH` (`js/reader.js`), puis corrigé le même jour : l'entrée globale `"$": "variable"` (pensée pour éviter qu'un `$1` isolé soit lu comme un montant en dollars) matchait aussi le `$` de `$(...)`/`$((...))` en Bash/Zsh/PowerShell/Git (substitution de commande, arithmétique), donnant "variable (cat..." au lieu d'une lecture cohérente. Repéré en testant l'exemple heredoc de `commandes-essentielles.md`. En creusant l'usage réel (`variables.md`/`fonctions.md` Bash et PowerShell), le problème dépassait largement Git : ajout de `"$(("`/`"$("` par contexte (bash/zsh : "arithmetic expansion"/"command substitution" ; powershell : "subexpression", terme propre à l'écosystème ; git : "command substitution"), ces clés plus longues étant prioritaires sur le `"$"` générique grâce au tri par longueur déjà en place.

En poursuivant la revue (audit systématique des spans `code` inline de chaque contexte contre sa table), 3 autres bugs sémantiques trouvés et corrigés le même jour, plus sérieux que de simples entrées manquantes puisqu'ils donnaient une lecture carrément fausse :
- **C** : `"&"` était toujours "address of", y compris pour le ET bit à bit (`n & 1`, `x & MASQUE` dans `operateurs-binaires.md`). Distingué par espacement : `"& "` (avec l'espace, clé plus longue donc prioritaire) capte l'usage infixe espacé (convention déjà suivie par tout le contenu du site pour les opérateurs binaires), `"&"` seul reste le préfixe non espacé (`&variable`, adresse). Ajouté au passage : `|=`/`&=`/`^=` (assignation bit à bit composée) et `++` (incrément), absents de la table.
- **C++** : même `"&"` toujours "address of", alors que tout l'usage inline réel en C++ (`const &`, `[&seuil]`, `[&]`) est une référence, jamais une adresse brute (le C++ enseigné ici préfère les références aux pointeurs bruts). Corrigé en "reference". `++` ajouté aussi (`++it`).
- **DSL/SQL** : la catégorie DSL (`regex.md` + `sql.md`) partage un seul contexte faute de subjects, mais `sql.md` réutilise `"*"`/`"$"`/`"."` avec un sens différent de `regex.md` (`SELECT *` lu "zero or more", `$pdo` lu "end anchor", `c.nom` lu "any character"). Le commentaire du code prévoyait déjà ce risque ("une future page DSL réutilisant '.' demanderait de scinder la catégorie en subjects") sans qu'il ait été vérifié empiriquement : la vérification a confirmé le problème, mais restructurer content/ en subjects pour un seul fichier aurait été disproportionné. Solution plus légère : `PAGE_SPECIFIC_CONTEXT`, un `Set` d'ids de page routés vers leur propre entrée dans `CONTEXT_OPERATOR_SPEECH` (ici `"sql"`) au lieu du contexte partagé, via `appState.curPageId` déjà disponible mais jusque-là inutilisé par le lecteur audio.

**Trouvaille plus large, même jour** : `CONTEXT_OPERATOR_SPEECH`/`GLOBAL_OPERATOR_SPEECH` ne couvrent que le code inline (span `code`) ; rien ne traitait les symboles typographiques utilisés directement dans le texte narré (prose, cellules de tableau). Audit du contenu rendu (fences et code inline exclus) : la flèche `→` apparaît ~90 fois dans des dizaines de fichiers, avec deux sens distincts selon le chapitre (plage numérique dans `entiers-et-debordements.md`/`encodage-des-textes.md`, "puis"/séquence/résultat partout ailleurs). Décision avec Louis : vérifier qu'aucun chapitre ne mélange les deux sens (confirmé, un script de classification par voisinage numérique n'a trouvé aucun vrai cas mixte) plutôt que d'analyser chaque occurrence individuellement, puis router par `curPageId` (même mécanisme que `PAGE_SPECIFIC_CONTEXT`) vers un mot différent par page. Formulation choisie en reprenant celle déjà utilisée par la prose existante de ces mêmes chapitres pour une plage ("va de 0 à 255" FR, "goes from 0 to 255" EN, "va de 0 a 255" ES/BR) plutôt qu'inventée. `≈`/`≥`/`≠`/`°` ajoutés au passage (sens unique, un mot par langue) ; `↔`/`±`/`…`/`·` isolé laissés de côté, trop rares (1-2 occurrences) pour justifier le travail. Nouvelle fonction `speakableText()`, distincte de `speakableCode()` (qui ne tourne que sur le code inline), avec un nouveau paramètre `pageId` propagé dans toute la chaîne d'appel (`buildReadingPlan` → `collectSegments` → `collectLeafSegments`).

## Séance d'écoute réelle en local (2026-08-15)

Serveur local (`scripts/dev.sh`) piloté via Chrome pour laisser Louis écouter directement les corrections du jour et donner un feedback immédiat, plutôt que de deviner le rendu audio depuis le code seul. Plusieurs allers-retours ont affiné/corrigé des choix faits plus tôt dans la session :
- **Emoji `📋`** : confirmé gênant à l'oreille ("porte-bloc récapitulatif"), retiré du texte envoyé à la synthèse (`DECORATIVE_EMOJI` dans `speakableText()`). Sans risque pour l'emoji cité en exemple pédagogique du chapitre encodage-des-textes.md, qui est dans un span `code` (`speakableCode()`), jamais dans le texte de prose que cette fonction traite.
- **`%`/`*` en C** : absents de la table, lus "percent"/"asterisk" au lieu de "modulo"/"times". Même ambiguïté que `&` (préfixe non-espacé = spécificateur printf/déclaration-déréférencement de pointeur, infixe espacé = modulo/multiplication) : même astuce d'espacement (`"% "`/`"* "` prioritaires sur les clés bare). Le cas préfixe (`%d`, `*ptr`) reste non traité, faute d'un mot qui couvrirait ses deux sens à lui seul.
- **`&` simplifié en "bitwise"** (au lieu de "bitwise and") : décision explicite de Louis après écoute, seulement pour `&` (`|`/`^` gardent leur nom complet pour rester distinguables à l'oreille).
- **`XOR`** : aller-retour en 3 temps avant la bonne réponse. D'abord respelé "ex or" partout (code ET prose) sur la foi d'un seul retour ambigu ; Louis a précisé que la prose disait déjà "XOR" correctement et que seul le symbole `^` posait problème (revert du remplacement en prose) ; puis a signalé que même en code "ex or" ne sonnait pas juste et voulait "XOR" comme en prose. Piste retenue : la voix TTS traite différemment un acronyme en MAJUSCULES (bien prononcé) d'un mot en minuscules ("xor", prononcé comme un mot inventé) — `"^": "bitwise xor"` devient `"^": "bitwise XOR"`. Toujours pas parfait à l'oreille sur la voix anglaise par défaut testée ; Louis juge que c'est une limite de cette voix plutôt qu'un bug côté site, laissé tel quel.
- **Fluidité de lecture pour du code trivial** (idée de Louis, pas un bug signalé) : chaque span `code` forçait un changement de voix FR/EN-US et une pause, même pour une simple variable isolée ("`a` et `a` deviendraient 0", "un `n` négatif"). `collectLeafSegments()` compare maintenant `speakableCode(code, context)` au texte d'origine : si rien n'a changé (aucun opérateur/drapeau CLI à réécrire), le code rejoint le buffer de la phrase environnante au lieu de forcer un changement de voix ; un span avec un vrai opérateur (`-3 % 2`) continue de basculer en anglais normalement.

## Bug TTS : mauvaise voix sur contenu BR

`document.documentElement.lang` recevait le code interne brut `"br"`, qui n'est pas une balise BCP-47 valide (`"br"` = breton en ISO 639-1) : le navigateur ne trouvait donc aucune voix portugais-brésilien. Corrigé par une table de correspondance code interne → BCP-47 (`br` → `pt-BR`) dans `js/lang.js`, sans changer le code interne du site.
