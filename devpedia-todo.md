## 6. Notions repérées pendant l'auto-review du module `nps_qualite` (Backoffice-TC)
Issu de l'auto-review du dépôt Backoffice-TC (mode `/review` auto-review), périmètre = module `nps_qualite` (scores NPS véhicules neufs/après-vente par concession, primes qualité). Module simple côté backend (un seul endpoint `/api/nps_qualite/villes`, non bloquant, cf. `NpsController::villes()`) ; l'essentiel de la logique est côté frontend (`public/js/modules/nps_qualite/{index,calculette}.js`), qui lit un fichier de données statique généré par un outil externe (`window.NPS_DATA`, aucune notion de code côté projet). Transverses déjà couvertes (PHP/PDO, routage front controller, appels HTTP natifs) non redétaillées ici. Points ci-dessous absents de Devpedia :
- **NPS (Net Promoter Score)** : métrique métier connue (mesure de satisfaction/fidélité client), calculée ici par `calculNPS()` (`calculette.js`) comme `(promoteurs − détracteurs) / total × 100` à partir d'une note de 1 à 10 (détracteurs = notes 1-6, neutres = notes 7-8 exclues du calcul mais comptées dans le total, promoteurs = notes 9-10). Usage général au-delà de ce projet : mesure standard de satisfaction client utilisée dans énormément d'entreprises (support, SAV, expérience produit), pas propre à l'automobile. Absent de Devpedia (aucun chapitre Gestion de projet/KPI ne le nomme).
- **`ResizeObserver`** : `watchQualityOverflow()` (`index.js`) observe la largeur réelle d'un tableau (`getBoundingClientRect().width`) pour basculer vers une mise en page resserrée dès qu'il déborderait de son conteneur, recalculé à chaque redimensionnement sans écouter l'événement global `resize` de la fenêtre. `observateurs-et-limitation-de-frequence.md` couvre déjà `IntersectionObserver` (visibilité) et `MutationObserver` (changement du DOM), mais pas `ResizeObserver` (changement de *dimensions* d'un élément précis) : même famille d'API navigateur "callback sur changement, sans sonder en boucle", troisième membre manquant. Bon candidat pour compléter ce chapitre existant plutôt qu'un nouveau.
- **Un ancêtre avec `transform` change le point de référence d'un descendant `position: fixed`** : `registerDropdown()` (`index.js`) réparente chaque panneau de menu déroulant sous `<body>` avant de le positionner en `position: fixed` (calcul manuel dans `placeDropdown()`), avec le commentaire "même piège que `.combo__panel` du design-system" -- signe qu'il s'agit d'un problème récurrent dans ce projet. Raison : `positionnement.md` explique que `fixed` se positionne par rapport à la fenêtre et qu'un `transform`/une opacité < 1 crée un nouveau *contexte d'empilement* (comparaison de `z-index`), mais ne dit pas qu'un ancêtre avec `transform` (ou `filter`/`will-change`) devient aussi le point de référence géométrique (*containing block*) de ses descendants `fixed` -- qui cessent alors de se positionner par rapport à la fenêtre. C'est ce second effet (pas le `z-index`) qui casse un menu `fixed` placé sous un ancêtre animé en `transform` (ici `.ds-reveal`), d'où le contournement par réparentage sous `<body>`. Distinction absente de `positionnement.md`.
- **`conic-gradient()` pour un anneau de progression circulaire sans SVG** : `.calc-ring` (`nps_qualite.css`) dessine l'anneau de progression de la calculette qualité avec `background: conic-gradient(var(--ring-color) calc(var(--pct) * 1%), var(--c-chip) 0)` sur un élément rond (`border-radius: 50%`) -- un dégradé dont la couleur tourne autour d'un point central (contrairement à `linear-gradient`/`radial-gradient`, qui progressent en ligne droite ou en cercles concentriques), utilisé ici pour remplir angulairement un pourcentage du cercle sans dépendre de SVG (`stroke-dasharray`) ni de JS pour dessiner la forme. Absent de Devpedia (aucun chapitre CSS ne mentionne `conic-gradient`).
- **API navigateur `Fullscreen`** (`requestFullscreen()`/`exitFullscreen()`/événement `fullscreenchange`) : le mode présentation (`index.js`) bascule la page en plein écran au clic, et écoute `fullscreenchange` pour resynchroniser son propre état si l'utilisateur quitte le plein écran par un raccourci navigateur (Échap) plutôt que par le bouton de la page -- point notable, l'événement est nécessaire précisément parce que le plein écran peut être quitté par un chemin que le code n'a pas déclenché lui-même. Absent de Devpedia.
- **API navigateur `Clipboard`** (`navigator.clipboard.writeText()`) : le bouton "Copier le résultat" de la calculette écrit dans le presse-papiers système ; asynchrone et pouvant échouer (autorisation refusée), d'où le `try/catch` autour de l'appel. Absent de Devpedia.

- **`table-layout: fixed` + `<colgroup>` pour des largeurs de colonnes autoritaires** (`nps_qualite.css`) : par défaut (`table-layout: auto`), un navigateur ajuste la largeur des colonnes au contenu réel des cellules ; `table-layout: fixed` fait l'inverse et impose les largeurs déclarées sur `<colgroup>` quel que soit le contenu, utilisé ici pour que plusieurs tableaux indépendants (un par marque) restent alignés colonne par colonne. Beaucoup de notions transverses déjà bien couvertes, vérifié avant d'aller plus loin : navigateur automatisé/Playwright et son fingerprinting (`attaques-navigateur-automatise.md`), `multiprocessing.Pool` fork/spawn (`parallelisme.md`), écriture concurrente dans un même fichier + un worker par fichier plutôt qu'un verrou partagé (`parallelisme.md`), motif Tee pour dupliquer `sys.stderr` vers un fichier de log (`sous-processus-et-flux-standard.md`, y compris le piège de ne pas le restaurer), format JSON Lines pour un fichier de reprise append-only (`manipuler-des-fichiers-et-dossiers.md`), `pyodbc`/SCD2 (`sql.md`). Le reste du projet est de la logique métier propre à ce programme (verdict de doublon par VIN/référence/caractéristiques, statuts cumulés Publiable/Vendable/volume de pack), pas des notions génériques à ajouter ici. Point absent, repéré en creusant le code au-delà du README :
- **Lire seulement le contenu ajouté à un fichier qui grossit, via un curseur de lecture retenu entre deux passages (`seek()`/`tell()`)** : `merge_child_logs()` (`src/scraper/run_logging.py`) fusionne en temps réel les fichiers de log de plusieurs processus enfants dans celui du parent, en interrogeant chaque fichier à intervalle régulier ; pour ne relire à chaque fois que les lignes écrites depuis le dernier passage (pas tout le fichier depuis le début), il retient la position atteinte (`f.tell()`) et y repositionne le curseur au passage suivant (`f.seek(position)`) avant de lire. C'est le mécanisme sous-jacent de la commande Unix `tail -f`/PowerShell `Get-Content -Wait` (déjà nommées côté shell dans `redirections-et-pipes.md`), jamais expliqué côté code applicatif (Python ou autre) : aucun chapitre ne montre comment implémenter ce suivi incrémental soi-même avec `seek`/`tell`.
- **Pipeline logiciel sur un pool fixe de N ressources, pour chevaucher la latence réseau sans multiplier les requêtes simultanées** : `_verify_pipelined()` (`src/scraper/duplicates.py`) répartit l'ouverture de pages d'annonce sur un pool de N onglets Playwright (`pages`) : au tour `i`, il démarre la navigation sur l'onglet `i % N` **avant** de finir d'extraire le résultat de l'onglet qui l'occupait au tour précédent (`i - N`) -- la navigation du tour suivant progresse donc pendant que l'extraction du tour courant se termine, sans jamais dépasser N requêtes en vol ni changer le délai entre deux navigations (seul le temps de rendu/extraction se chevauche). Motif générique (déborde largement le scraping), proche du *double buffering*, absent de Devpedia : aucun chapitre `Qualité, performance et outils/Performance` ne couvre le chevauchement d'E/S via un pool borné de ressources réutilisées en tourniquet.
- **Normalisation Unicode (NFKD) pour retirer les accents d'un texte** : `strip_accents()` (`src/scraper/browser.py`) fait `unicodedata.normalize("NFKD", texte)` puis filtre les caractères combinants (`unicodedata.combining(c)`) -- NFKD décompose chaque caractère accentué en sa lettre de base suivie d'un diacritique séparé (`é` devient `e` + `´`), qu'il suffit ensuite d'écarter. Une des 4 formes de normalisation Unicode standard (NFC/NFD/NFKC/NFKD), utile dès qu'il faut comparer ou rechercher du texte en ignorant les accents (ici, regrouper des titres d'annonces malgré des variations d'écriture). Absent de Devpedia (`encodage-des-textes.md` couvre l'encodage/BOM/mojibake, jamais les formes de normalisation Unicode).
- **`navigator.webdriver` : le signal concret que les anti-bots lisent pour détecter un navigateur piloté, et son contournement** : `cli.py` lance Chrome via Playwright avec `context.add_init_script("Object.defineProperty(navigator, 'webdriver', {get: () => undefined})")` -- tout navigateur conforme au protocole WebDriver (Selenium, Playwright...) expose par défaut `navigator.webdriver === true`, une propriété JavaScript lisible par n'importe quelle page et donc par les systèmes anti-bot (DataDome et consorts, déjà nommés dans ce même projet) pour distinguer un humain d'un script ; la réécrire dès le chargement de la page (avant tout autre script) la masque. `attaques-navigateur-automatise.md` mentionne déjà vaguement un "fingerprinting du pilote automatique" (propriétés JS spécifiques à Playwright/Selenium) sans jamais nommer cette propriété précise ni sa contre-mesure : extension utile du chapitre existant. Profil Chrome persistant (`launch_persistent_context(user_data_dir=...)`, cookies/session conservés entre deux exécutions) accompagne la même logique côté projet, mais reste un simple paramètre Playwright, pas une notion à part.
- **Repli local avec resynchronisation différée (« store-and-forward »)** : `audit_history.py` écrit l'historique de chaque audit dans la base applicative (SQL Server via `pyodbc`) mais, si elle est injoignable, bascule sans lever d'exception sur un fichier SQLite local (`_connect_tech()` renvoie `None`, jamais une erreur qui remonte) ; chaque ligne locale porte un indicateur `synced_to_tech = 0`, et au tout début de l'audit suivant où la base applicative redevient joignable, `_sync_pending_to_tech()` rejoue chaque audit local encore marqué non synchronisé vers elle, un par un (commit après chaque audit poussé avec succès, pour qu'un échec en cours de route laisse les audits déjà poussés définitivement synchronisés et ne fasse retenter que les suivants). Pattern de résilience générique (continuer à fonctionner en écrivant localement pendant une panne du système distant, puis rattraper l'écart une fois qu'il revient), absent de Devpedia : aucun chapitre ne le nomme, que ce soit côté bases de données ou architecture.
- **Lire le JSON `__NEXT_DATA__` embarqué par Next.js plutôt que parser le HTML rendu** : `leboncoin.py` (`LBC_NEXT_DATA_JS`) récupère les caractéristiques d'une annonce en lisant directement `document.getElementById('__NEXT_DATA__').textContent` et en le parsant comme du JSON (`json.loads(raw)["props"]["pageProps"]["ad"]["attributes"]`), plutôt que d'aller chercher chaque valeur dans les éléments HTML affichés. `ssr-vs-csr.md` explique déjà l'hydratation et recommande en bonne pratique de "transmettre explicitement les données au client plutôt que de les recalculer" côté framework SSR (Next.js/Nuxt cités), mais ne nomme jamais le mécanisme concret qui porte ces données dans la page (la balise `<script id="__NEXT_DATA__" type="application/json">`, injectée par Next.js pour l'hydratation) ni son détournement classique en scraping : lire ce JSON structuré est bien plus stable qu'analyser le rendu HTML, qui change à chaque refonte visuelle du site alors que la forme des données change beaucoup plus rarement. Extension utile du chapitre existant.
