Bloque un run exactement comme un Variable Group non autorisé (même bandeau "Permission needed"), mais la résolution est différente : validation/approbation par l'approbateur désigné, pas un simple octroi d'accès. - **Piège Python `os.environ.get(cle, defaut)` : le défaut ne s'applique QUE si la clé est absente, jamais si sa valeur est une chaîne vide** : `projects/nps_qualite/src/staging/config.py:39-46` -- un Variable Group Azure DevOps peut déclarer une variable avec une valeur vide plutôt que de l'omettre (visible dans l'UI mais facile à rater), auquel cas `os.environ.get("X", "50")` renvoie `""`, pas `"50"` (`os.environ.get` ne teste que la présence de la clé, jamais la valeur associée) -- a fait planter `int(os.environ.get("NPS_MIN_ROWS_TOTAL", "50"))` avec `ValueError: invalid literal for int() with base 10: ''` en run réel. Fix : `os.environ.get("X") or "50"`. Chapitre `content/Langages/Python/modules-et-environnements.md` couvre déjà `os.environ.get(cle, defaut)` (bloc `os.environ["CHEMIN_CONFIG"]` / `.get(...)`) mais uniquement le cas clé absente, jamais ce piège valeur-vide-déclarée.
- **`sqlcmd` : variables de script (`-v NOM=valeur`, `$(NOM)`, `:setvar`)** : `projects/nps_qualite/sql/ddl/staging_schema.sql:29-36` -- un script `.sql` exécuté via `sqlcmd -v DBNAME=PP_DWH_STAGING -i script.sql` peut référencer `$(DBNAME)` dans le corps du script (ex. `USE [$(DBNAME)];`), substitué avant exécution -- paramétrer un même script pour plusieurs environnements (pprod/prod) sans le dupliquer ni le générer dynamiquement. Garde défensive courante si la variable n'est pas passée : `IF '$(DBNAME)' = '' OR '$(DBNAME)' = '$' + '(DBNAME)' RAISERROR(...)` (le second test attrape le cas où `$(DBNAME)` n'est même pas substitué et apparaît tel quel). `:setvar NOM valeur` fait la même chose direct dans le script plutôt que via `-v` en ligne de commande. Absent de `content/Langages/Domain-specific Languages (DSL)/sql.md` (la section "Piloter SQL depuis Python avec pyodbc" n'aborde pas `sqlcmd` en CLI) et absent de `content/Infrastructure & DevOps/CI-CD/`.
- **Authentification Windows intégrée (Kerberos/NTLM) pour SQL Server (`Trusted_Connection=yes`) : distinguer un échec d'authentification d'un échec d'autorisation** : `tools/common/db.py` (chaîne pyodbc `Trusted_Connection=yes`) -- avec cette option, le client ne présente aucun login/mot de passe : Windows négocie l'identité (Kerberos si un contrôleur de domaine est joignable, sinon repli NTLM) en coulisses, et SQL Server reçoit une identité déjà authentifiée. Vérifié en confirmant que l'identité passait bien sur une autre instance (login existant) avec la même machine/compte.
